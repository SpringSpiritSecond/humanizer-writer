# 去 AI 味工作流：编排与闸门

- 起草：2026-11-11
- 前置文档：[评测方案-台词与口播](评测方案-台词与口播.md)、[课题背景与首轮调研](去AI味-课题背景与首轮调研.md)

流水线由两部分组成：固定的骨架，以及骨架上可以替换的槽位。闸门属于骨架，不管最后哪个 skill 胜出都不变。skill 只放在槽位里，具体放哪个由盲审决定。评测和生产跑的是同一套代码：评测时每个参赛者对应一份槽位配置，生产时只用胜出的那一份。

## 1. 骨架

```
S0 brief 校验 ──硬── 缺事实 / 缺场景卡 → 退回
S1 生成       ← 槽位 A，出 N 份
G0 格式 ──────硬── 长度/时长、必含词、锁定台词、禁用词
S2 检测 ──────报告── 标出命中位置
S3 改写       ← 槽位 B + 槽位 C，只改命中处；没命中就原样放行
G1 合规 ──────硬── 口播线：极限词拒，豁免区转复核
G2 保真 ──────硬── 事实、beat、承诺；新增细节也算
              （每轮 S3 之后都重跑 G1、G2）
G3 风格计量 ──软── 超标 → 带命中位置回 S3，轮数上限 = 槽位 D
G4 LLM 裁判 ──软── 放行 / 转人工 / 重写；裁判换一家厂商
G5 检测器 ────监控
S4 人工抽检 ── 结果流回工作台
```

| 阶段 | 类型 | 不过时怎么办 | 需要模型 |
|---|---|---|---|
| S0 | 硬 | 退回 brief | 否 |
| S1 | 槽位 A | — | 是 |
| G0 | 硬 | 这一份淘汰 | 否 |
| S2 | 报告 | 只出命中位置 | 否 |
| S3 | 槽位 B、C | — | 是 |
| G1 | 硬 | 拒；豁免区转复核 | 否（模糊区以后可接） |
| G2 | 硬 | 带出错的字段回 S3；轮数用完转人工 | 否（beat 语义比对以后可接） |
| G3 | 软 | 带命中位置回 S3 | 否 |
| G4 | 软 | 校准前只记录，中间分一律转人工 | 是 |
| G5 | 监控 | 只记录 | 外部 |

## 2. 编排规则

1. skill 不给自己当裁判。闸门要么是代码，要么是没参与写稿的另一家模型。
2. 硬闸门只拦能确定判断的问题，并且每轮改写之后都要重跑。
3. 软闸门只分流，不拦截。打回时附上命中的具体位置，只做定向改写；重写轮数有上限，到了上限就转人工。
4. 每条线的例外写进同一份 profile（`profiles/<线>.json`），S2、S3、G3 都读这一份。
5. 一个槽位放几个 skill、按什么方式组合（先后串联，还是合并成一个 prompt），写进配置，由盲审来选。
6. 阈值一律从工作台的标注数据来。数据到之前，G3 和 G4 都只记录，不自动放行。
7. 决策门只在两种情况停下来问人：合规判断落在模糊区（转法务），以及成稿要对外发布。

## 3. 接口约定

各阶段由不同的人分头实现，以下约定必须遵守。修改约定要先改本文档。

### 3.1 阶段函数

```python
def run(ctx: dict) -> dict: ...
```

`ctx` 的字段：

| 字段 | 说明 |
|---|---|
| `line` | `"台词"` 或 `"口播"` |
| `brief` | 符合 `eval/briefs/<线>/_template.json` 结构的 dict |
| `profile` | `profiles/<线>.json` 读出来的 dict |
| `text` | 当前稿件，已经做过统一格式处理；统一格式时必须保留换行，因为“段”按换行切分 |
| `round` | 当前改写轮次，从 0 开始 |
| `history` | 之前各阶段的结果列表 |
| `batch_texts` | 同一 brief 下的其他候选（G3 计算批次内多样性时用）；可以没有 |
| `config` | 这一阶段在配置里的参数 dict |
| `adapter` | 模型适配器实例；只有槽位阶段（S1、S3）和 G4 会用到 |
| `rewrite_hits` | 交给 S3 的命中，来自打回它的那道闸门 |
| `rewrite_from` | 打回 S3 的是哪个阶段，例如 `"G2"` |

返回的结果：

```json
{
  "stage": "G2",
  "kind": "hard | soft | report | monitor | slot",
  "verdict": "pass | fail | route | review",
  "route_to": "S3 | human | null",
  "hits": [
    {
      "rule": "not_x_but_y",
      "span": [12, 30],
      "excerpt": "不是……而是……",
      "severity": "block | warn | hint",
      "message": "给改写看的一句话：删掉，或换成具体信息"
    }
  ],
  "metrics": {}
}
```

- `span` 是统一格式之后的文本里，Python `str` 的字符下标，左闭右开。问题针对全文、没有具体位置时（例如长度不对、字段缺失），`span` 为 `null`。
- `verdict`：`pass` 表示放行；`fail` 表示硬拦，这一份稿件结束；`route` 表示打回给 `route_to`；`review` 表示转人工复核。
- 槽位阶段的 `kind` 为 `slot`。S1 在结果里多返回 `texts`（生成的 N 份稿件），S3 多返回 `text`（改写后的稿件）。
- 阶段在配置里写成点分路径，例如 `"S2": "detect.stages:s2"`。runner 按路径导入，没有配置的阶段就跳过。
- 每轮 S3 改写之后，按 S2 → G1 → G2 → G3 的顺序全部重跑。S2 只出报告、成本很低，但改写后上一轮的命中位置已经失效。S3 只处理打回它的那道闸门给出的命中。
- G2 在轮数用完后仍不过时，记录 `status=human`（生产语义：转人工），同时记录 `layer1.survived=false`（评测语义：第一层出局）。导出给工作台时按评测语义处理。

### 3.2 规则 id

S2、G3 和 profile 用的是同一套规则 id。第一批如下；新增 id 时要同时补进这张表。闸门自己的规则 id 不在这张表里，统一加阶段前缀（`s0.*`、`g0.*`、`g1.*`、`g2.*`），以免和风格规则混用。

| id | 说明 | 档位 |
|---|---|---|
| `not_x_but_y` | 不是 A 而是 B、不仅仅是 A 而是 B、不只是 A 更是 B、与其……不如；正常递进句（不仅……还……）不算 | 单次即标 |
| `batch_diversity` | 同一 brief 下几份候选彼此太像（distinct-n、self-BLEU） | 计量 |
| `exclaim_density` | 句末感叹号占比：情绪靠标点撑，不靠内容 | 计量（`exclaim_ratio`） |
| `fragment_ratio` | 4 字以内碎句占比：话没说完整 | 计量（`fragment_ratio`） |
| `bare_imperative` | 没头没尾的短口令：听不出对谁说、为什么 | 计量（`bare_imperative_ratio`） |

后三条来自第一轮盲审（2026-11-12），针对的是一个通用问题：文字是写给一个“需要被交代清楚的旁观者”的，而不是写给真正的听话人。台词里表现为角色互相报告观众已经看到的事，科普和口播里表现为宣讲知识点、播报卖点。这三条都按句计算，只由拟声词和叹词组成的句子不计入。各文体能容忍多少，放在 profile 的阈值里设，不写死在规则里。
| `heading_density` | 小标题过密 | 计量 |
| `connector_density` | 首先 / 此外 / 总之 类连接词 | 计量，低权重 |
| `buzzword` | 赋能 / 打造 / 闭环 类词 | 计量，低权重 |
| `synonym_rotation` | 刻意换同义词 | 计量 |
| `uniform_length` | 句长或段长过于齐整 | 计量 |
| `de_stacking` | 连着用好几个“的” | 同段 ≥2 才标 |
| `jinxing_verb` | 进行 + 动词 | 单次即标 |
| `bei_stack` | 被字句连用 | 同段 ≥2 才标 |
| `four_char_parallel` | 空洞的四字排比 | 同段 ≥2 才标 |
| `cliche_opening` | “随着……的发展”一类开头 | 单次即标 |
| `cliche_ending` | 套话收尾、拔高收尾 | 单次即标 |
| `colon_conclusion` | “核心是：”一类结论式冒号 | 单次即标 |
| `dash` | 破折号 | 同段 ≥2 才标 |
| `semicolon_dunhao` | 分号、顿号过密 | 计量 |
| `rhetorical_question` | 设问 | 同段 ≥2 才标 |
| `triple_parallel` | 硬凑三点 | 单次即标 |
| `punchline_ending` | 金句收尾 | 单次即标 |

“单次即标”指出现一次就标记。“同段 ≥2 才标”指同一段里出现两次以上才标记。“计量”指不标单个位置，只计算密度，交给 G3 处理。

### 3.3 profile

格式见 `profiles/台词.json` 和 `profiles/口播.json`。字段的意思：

- `rules.<id>`：`"on"`、`"hint"`（只提示，不打回）、`"off"`。没写的规则按 `"on"` 处理。
- `exceptions`：这条线允许的写法，例如破折号表示打断。检测器遇到这些写法不标记，改写也不碰。一条例外可能只归某一个阶段管：`first_episode` 归 G1；`children_screen_recap` 和 `action_line_adverbs` 归 S3，以及以后的语义规则；S2 遇到不归它管的例外就不处理。
- `length`：长度怎么算、容差多少。
- `compliance`：合规闸门是否启用，以及涉及哪些行业。
- `fidelity`：哪些字段必须逐字一致。

### 3.4 配置

每个参赛者，以及最终上线的版本，各对应一份 `configs/<名字>.json`：线、profile、各角色用的模型、槽位 A–D 放什么、每个阶段的点分路径和参数、git hash。

## 4. 和盲审的关系

- 评测时：每份配置跑同一套骨架。被 G0–G2 刷掉的稿件就算第一层淘汰，剩下的导出成工作台 `workbench import` 能读的格式。
- 上线时：胜出的配置升为这条线的生产配置，并锁定 git hash。之后要换 skill 或改阈值，都得先在冻结集上过盲审的替换条件。

## 5. 第一期范围

不调用任何模型，先把不依赖模型的部分做出来：

- **骨架与硬闸门**（`pipeline/`、`configs/`）：runner、按点分路径加载阶段、轮次控制（每轮改写后重跑 G1、G2）、S0、G0、G1、G2；S1、S3、G4 先做成可插拔的模型适配器，测试时用假适配器；运行报告输出，以及导出成工作台导入格式。
- **检测与风格计量**（`detect/`）：S2 规则检测，带位置、两档触发，按 profile 放行例外；G3 计量（标点密度、小标题密度、句长变异系数、批次内多样性），阈值从配置读，默认只记录。

两部分各自开分支、开 PR，互不改对方的目录。`profiles/` 和本文档由主会话维护。
